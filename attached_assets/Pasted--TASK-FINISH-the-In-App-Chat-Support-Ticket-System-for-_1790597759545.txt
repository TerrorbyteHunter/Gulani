## 1. GOAL
A Taobao-style messaging system inside the app (web-responsive now, with an API designed so the future native mobile app can reuse it), with THREE conversation types:

A. BUYER ↔ VENDOR chat (pre-sale questions, order questions, after-sale)
B. CUSTOMER ↔ CUSTOMER SERVICE chat
C. VENDOR ↔ CUSTOMER SERVICE chat

Types B and C are TICKETS with a lifecycle, assignment, priority, and a resolved/closed state. Type A is a normal chat, but either party can escalate it to customer service, which creates a linked ticket.

## 2. ROLES & ACCESS
- Customer: chat with vendors (from product, shop, or order pages); open and view own support tickets.
- Vendor: chat with their own customers only; open and view own support tickets.
- Customer Service agent (existing "Customer Service" admin role): support inbox, reply, assign, escalate, resolve.
- Master Admin / System Admin: full access, settings, reports, and read access to any conversation for dispute resolution (always audit-logged).
- Guest checkout users: limited support chat tied to their order number plus phone/email verification. Buyer↔vendor chat requires an account.
- Enforce everything server-side on every API route and socket event. Add any missing permissions to the existing RBAC, e.g. chat.use, support.view_inbox, support.reply, support.assign, support.resolve, support.reopen, support.view_all_conversations, support.manage_settings, support.view_reports, support.manage_canned_replies.

## 3. DATA MODEL (follow existing naming conventions; add only what is missing)
- conversations: type (buyer_vendor | customer_support | vendor_support), buyer_id, vendor_id, context_type (product | order | shop | general), context_id, status, last_message_at, last_message_preview, timestamps.
- conversation_participants: user_id, role_in_chat, last_read_message_id, muted, joined_at, left_at (supports multiple agents over time).
- messages: conversation_id, sender_id, sender_role, type (text | image | file | product_card | order_card | system | internal_note), body, metadata JSON, reply_to_message_id, client_message_id (idempotency), delivery status, edited_at, deleted_at. internal_note messages must NEVER reach buyer/vendor clients.
- message_attachments: file_url, type, size, thumbnail_url.
- tickets: ticket_number (e.g. GUL-000123), conversation_id, requester_id, requester_type (customer | vendor), category, subject, priority (low | normal | high | urgent), status, assigned_agent_id, related_order_id / product_id / vendor_id, source_conversation_id (for escalations), first_response_at, resolved_at, closed_at, resolution_code, resolution_note, csat_rating, csat_comment, timestamps.
- ticket_events: full history timeline (created, assigned, status/priority changed, escalated, note added, reopened, resolved, closed) with actor, old/new value.
- ticket_categories (admin-managed, separate lists for customer and vendor tickets), e.g. Order issue, Payment issue (mobile money/Visa), Delivery, Refund/Return, Product issue, Vendor payout, Account, Listing approval, Dispute, Other.
- canned_replies, chat_reports, blocked_users, and chat_settings (admin-editable: support hours, auto-reply text, SLA targets, auto-close days, max file size, allowed file types, banned words, contact-masking on/off).
Add proper indexes on conversation_id + created_at, user_id, status, assigned_agent_id, ticket_number.

## 4. REAL-TIME MESSAGING
- WebSockets (or the best fit for this stack), authenticated with the existing session, with server-side authorization for joining each conversation.
- Instant send/receive, typing indicators, presence/last seen, delivery states (sent → delivered → read), unread counts per conversation and in total, upward infinite-scroll pagination (30 at a time), optimistic UI with retry, auto-reconnect with catch-up of missed messages.
- Graceful polling fallback for weak mobile connections. Keep payloads small and lazy-load images, since many users are on slow mobile data.
- Idempotent sends via client_message_id so retries never create duplicates.
- Per-user rate limiting to stop flooding.

## 6. TICKET WORKFLOW
Statuses: New → Open → Pending (waiting on requester) → On Hold → Resolved → Closed. Reopen allowed within a configurable window (default 7 days).
- Creation: automatic when a customer or vendor starts a support chat, with an auto-acknowledgement system message showing the ticket number and expected response time.
- Assignment: shared unassigned queue; agents can "Take" a ticket; admins/supervisors assign or reassign; optional round-robin auto-assign (setting, off by default); collaborators allowed.
- Status automation: agent reply → Pending; requester reply → Open; no reply for X days → reminder, then auto-close.
- Resolving: agent marks Resolved with a required resolution code and note. Requester is notified and can confirm, reopen, or ignore (auto-closes after X days). Closed tickets make the chat read-only with a banner offering to start a new ticket or reopen. After resolution, show a 1–5 star CSAT rating plus optional comment.
- Escalation from buyer↔vendor chat: "Report a problem / Get help from Gulani" button creates a ticket linked to the original chat and order, posts a system message in the original chat, and lets customer service view the history (audit-logged) and join as a third participant labeled "Gulani Support".
- Internal escalation: an agent can escalate to a supervisor or to another admin role (Order Manager, Finance Admin, Vendor Manager) with a note.
- Priority and SLA: configurable first-response and resolution targets per priority, with countdown/overdue badges in the inbox and overdue tickets surfaced at the top.
- Internal notes with @mentions, visible to staff only.
- Basic linking of duplicate tickets.
